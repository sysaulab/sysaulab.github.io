Project Retrospective

Animation as data, engine as loop.

In 2012 a Maple board — ARM, Arduino-compatible — could drive ten PWM LEDs. The obvious way to make them pulse was to put delay() calls in the sketch. This project did something else: it made each animation a chain of keyframes, and let a single 100 Hz loop walk every LED through its own chain. The animation became data. The engine became a loop.

What it was

The board was a LeafLabs Maple: an STM32F103, ARM Cortex-M3, with an Arduino-compatible API but its own hardware calls — SerialUSB, BOARD_LED_PIN, a PWM mode constant, pwmWrite, toggleLED. The project was called SoftLed 0.1 Alpha, written by Sylvain Saucier in January 2012.

The problem it solved is ordinary. A microcontroller has a handful of PWM pins. You want to fade LEDs up and down, pulse them, make them breathe, chain one effect into another. The naive approach is to write each animation as a sequence of pwmWrite calls interleaved with delay: 

pwmWrite(led, 128);
delay(500);
pwmWrite(led, 255);
delay(500);

That blocks everything else. Only one animation can run at a time. Ten LEDs mean ten seconds of dead CPU. The animation is a script, and the script is the system.

The core idea: separate the animation from the execution. An animation is a chain of steps — each step is a target value, a duration, and a pointer to the next step. The engine is a single loop that, every ten milliseconds, checks whether each LED's current step has expired, and either advances to the next step or interpolates the current value toward the goal. No delays. No blocking. Ten LEDs, ten animations, one loop.

The animation is a linked list. The engine is an interpreter. The serial protocol is a way to edit the list from a host. That is the whole design.

How it worked

A program step is three numbers: { target, wait, next }. Fade to target over wait milliseconds, then jump to step next. Program zero is special: it means “stay where you are, load nothing new.” A program chain is a linked list of steps. Because next is an index, chains can loop — 1 → 2 → 1 gives a pulse — or terminate — → 0 gives a one-shot fade that stays.

The setup in the source defines six programs. Two of them form a pulse loop; two form a breathing loop; two are one-shot fades to full and to off: 

Program 1: 65535 ──250ms──▶ 2      ┐
Program 2: 0     ──250ms──▶ 1      ┘  500ms pulse, full to off

Program 3: 55535 ──750ms──▶ 4      ┐
Program 4: 10000 ──750ms──▶ 3      ┘  1.5s breathing, 15% to 85%

Program 5: 65535 ──60s────▶ 0          one-shot fade to full, stay
Program 6: 0     ──60s────▶ 0          one-shot fade to off, stay

An LED is { pin, program, value, goal, deadline }. Adding an LED registers its pin, sets its initial goal and program pointer, and starts it at value zero. From then on the loop drives it. An LED is just a cursor into a program chain.

The loop — _led_update, scheduled every 10 ms — is the whole engine: 

for each LED:
    if time >= deadline:
        value = goal
        if program > 0:
            next = Progs.next[program - 1]
            if next > 0:
                deadline = time + Progs.wait[next - 1]
                goal     = Progs.target[next - 1]
            program = next
    else:
        value = map(time, last_time, deadline, last_value, goal)
    pwmWrite(pin, value)
last_time = time

Two things are worth noticing. First, interpolation and program advance are the same mechanism. One branch handles “deadline reached” and jumps to the next program; the other handles “deadline not reached” and interpolates. There is no separate animation engine — the loop is the engine. Second, the interpolation uses absolute timestamps at both ends: the last tick and the deadline. A skipped tick does not break the animation, because the next tick catches up. The fade is a function of time, not of iterations.

The protocol is ASCII, fixed-width, and terminated with #. Six commands, in three pairs — get, set, add, for each of LED and program: 

GL#                              get LEDs          (stub)
GP#                              get programs      (stub)

SLlllgggggddddddddddppppp#       set LED           (26 chars)
SPpppppgggggddddddddddnnnnn#     set program       (28 chars)

ALnnngggggddddddddddppppp#       add LED           (26 chars)
APgggggddddddddddnnnnn#          add program       (23 chars)

n is a pin, l an LED index, p a program index, g a goal value (0–65535), and d a duration in milliseconds. The commands are human-readable and human-typeable. You can drive the whole system from a serial terminal.

There is one asymmetry worth flagging because the source flags it too. AL takes a pin, because the LED index is assigned by the firmware as LEDs are added. SL takes an LED index, not a pin. The comments carry the warning — !NOT THE LED PIN! on set, !WILL NOT BECOME THE LED NUMBER! on add — because the author knew it was a trap. Add by pin, remember the index, set by index.

The pieces

The firmware is small and conventional for its moment: three libraries, a task table, and a serial command parser.

Animation

led_lib.pde

The program and LED databases, the update loop, and the add/set/get wrappers. This is the engine: program chaining, linear interpolation, PWM output.

Control

control_lib.pde

The serial command parser. Reads characters into a buffer, recognizes #, looks up the command pair, dispatches through a function table, resets.

Setup

softled.pde

Constants, data structures, the command table, the task table, and the user configuration section where the example programs and LEDs are defined.

Scheduler

Tasks

One task, ten milliseconds, _led_update. Extensible in principle — MAXTASK is a constant — but used with exactly one entry.

Where the design met its edges

The model is clean. The implementation is small, direct, and — in a few places — one byte past the end of an array. These are the interesting parts, because they show what a parser written for a cooperative host looks like when the host is not always cooperative.

Two off-by-one bounds checks

The command buffer is uint8 command[32], valid indices 0–31. Incoming characters are stored with command[++command[0]] = SerialUSB.read(); — pre-increment the length counter, write at that index. The overflow check is if (command[0] > COMMAND_LENGTH) resetcommand();, which runs after the write and is off by one: at command[0] = 32 the code writes command[32] (one past the end) and the check still passes, because 32 > 32 is false. The next character writes command[33] and only then resets. Two bytes past the buffer, every time a long command arrives without a #. The fix is >= and checking before the write.

The command lookup loops have the same shape. The bound is xb > CMD_REF_0_SIZE, but the array has size CMD_REF_0_SIZE, so valid indices stop one lower. And because || evaluates left to right, the code reads _com_ref_0[xb] before checking the bound. On a failed lookup it reads two elements past the end of the table before exiting. Reordering the operands, or using >=, would prevent it.

A helper that looks pure and is not

atoint() converts a fixed-width ASCII field to an integer. It uses the global xb as its digit-place multiplier. It works — callers reset xb before use, and resetcommand() zeroes it afterwards — but it means a helper that reads like a pure function is mutating shared state. Any future caller that needed xb to survive across an atoint() call would be quietly wrong.

Truncated parameters

SP parses the program index with five digits — up to 99,999 — and passes it to Progs.set, whose first parameter is uint8. Same for the program argument of AL. With MAXPROGRAM = 100 the truncation is harmless in practice, but nothing in the parser rejects an index that exceeds the table.

Getters that do nothing

GP# and GL# call Progs.get() and Leds.get(), which are empty stubs. The source comments call them “BUGGY AT THE MOMENT” and “BROKEN NOW”. The command table has room for read-back, and the protocol reserves slots for it, but read-back was never finished. There is no way to ask the board what state it is in.

A return value nobody reads

control() returns 1 when it has executed a command, and its comment says this is to “allow only 1 task to be launched every loop.” But loop() calls control() and ignores the return value, then unconditionally runs the task list. The return value documents an intent the caller does not honour. In practice it does not matter — control() returns as soon as it executes one command, so the intent is satisfied anyway — but the code claims a guarantee it does not enforce.

The arithmetic of time

map(_time, Leds.time, Leds.deadline[xb], ...) divides by (deadline - Leds.time). If an LED is set with wait = 0, deadline equals millis() and the next tick goes through the program branch, skipping the division — unless the tick lands exactly on the deadline. Rare, but not excluded. Separately, millis() wraps every ~49.7 days; the code compares raw values, so after a wrap every LED believes its deadline is in the far past and jumps to its goal. A run longer than seven weeks would reveal both.

Comments that do not match the code

The example serial strings in the source comments are not all faithful. Several of the AL examples omit the trailing # that the parser requires. The comment for program 4 repeats the target value from program 3 — 55535 instead of 10000. These are documentation bugs, not code bugs, but they are the kind that cost an hour to a reader who trusts the comment over the call.

The shared lesson: each of these is a place where a design that is correct under cooperative assumptions becomes fragile under adversarial ones. A command parser is an input parser, and input parsers need bounds checks that are right by one, not approximately right. The rest of the system — the program model, the interpolation, the loop — is sound. The edges are where the bugs live.

What this is — and what it is not

This is a working firmware for a specific board (Maple, 2012) that implements a general model: a chain of keyframes, a per-LED program pointer, and a single loop that does both interpolation and program advance. It ran on real hardware. The example chains in setup() — pulse, breathe, fade-to-stay — are the expected use cases, and they work.

It is not a finished product. The getters are stubs. The parser has two off-by-one bugs in its bounds checks — the kind that do not fail visibly on a small command set with cooperative input, which is why they survived. The protocol has no framing, no checksum, no acknowledgement, and no error reporting. The global scratch variable is fragile. The comments drift from the code in several places.

It is also, structurally, an early statement of a pattern. Animation as data, engine as loop — the same shape appears in modern LED libraries, usually with the same separation between timeline and driver. This project did it in a few hundred lines for a board with 20 KB of RAM and no floating point.

The honest summary: the model was right, the implementation was good enough to demonstrate it, and the constraints that made it necessary — 8-bit microcontrollers, no dynamic allocation, one loop — are the constraints that make the pattern clear. Modern microcontrollers have room for a heavier engine, and mostly that is what people use. But the shape is the same, and it started here.
