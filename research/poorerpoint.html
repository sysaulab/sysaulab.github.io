What is PoorerPoint?

PoorerPoint is a presentation engine that runs in your terminal. You write your slides in ordinary markdown. You run one command. You press the spacebar to advance. That is the whole interface.

It exists because presentation software has spent thirty years adding features and forgetting the one thing that actually makes a talk readable: the header should stay on screen.

The core idea: a deck is not a pile of slides. It is a single document where headers persist, content accumulates, and only the thing that actually changed gets animated. A header stack is sticky. Everything below it flows.

There are no themes, no layout tools, no transition timeline, no per-object entrance triggers. There is markdown, a terminal, and the spacebar. The constraint is the feature.

Why it exists

PowerPoint has no concept of "this header stays on screen." Every slide is a fresh pile of independent objects, and persistence is something you simulate by hand — copy the same text box N times, tune entrance and exit triggers to the millisecond, and hope it reads as one thing that never moved.

It is a lie told with an animation timeline, and it costs a half-night before every presentation.

PoorerPoint has the concept. A header stack is sticky: a new header replaces the same-or-higher level and everything below it, and the rest stays put. The only thing that animates is what actually changed. Titles slide in from the right in 333 ms — enough to notice, not enough to steal the show. Bullets follow. Then nothing moves until you press space.

The point is not the animation. The point is that writing a deck in plain markdown forces you to commit to a structure before you touch a font. If the heading levels don't make sense as text, they won't make sense as slides, and no theme will save them.

How it works

A deck is just a markdown file. Headers are titles and subtitles. Content under a header is a slide. The engine parses the file into a stack of headers, then walks through it one content block at a time.

The rules

  • Headers form a stack. Each level indents one space. H1 flush left, H2 one space, H3 two, and so on. In practice you rarely need more than four.
  • A header persists until another header of the same or higher level replaces it. Lower-level headers under it are dropped too.
  • A slide is a stack state plus the content beneath it. The next header that has content starts the next slide.
  • Headers with no content are skipped. No empty slides.
  • Consecutive headers merge. An H1 followed immediately by an H2 renders as a stacked title block, not two slides.

What markdown is supported

Headers (# through ######), paragraphs, bold, italic, inline code, nested bullet lists, fenced code blocks, horizontal rules, and tables with alignment.

Tables that fit

Tables are measured against the terminal width. Column widths are computed two ways — the natural width of the full cell text, and the floor below which wrapping would break a single word — then distributed proportionally when the table doesn't fit. Long prose wraps. Long unbreakable words are allowed to push the table past the right edge rather than break mid-word.

Persistence is free. The engine keeps a longest-common-prefix diff against the previous slide. Lines that didn't change were never re-entered, so they never needed to be re-hidden. The unchanged parts of a slide simply stay where they are.

The keys

Six keys. One of them is the spacebar. The rest are there for the presenter who needs them.

Key Action
Space Next slide. Ignored while animating — never buffered.
→ / l Next slide. Always live; resets and replays the animation.
← / h Previous slide. Resets and replays the animation.
↓ / j Scroll content down. Resets on slide change.
↑ / k Scroll content up. Resets on slide change.
q / Esc Quit.

Content that overflows the viewport is auto-scrolled so new material is always visible. Manual scrolling is there for the presenter when a slide runs long.

The web port

There is a web application version of PoorerPoint. It is not documented in the terminal tool's manual — this page is where it gets its first mention.

The web port is not a wrapper around the terminal engine. It is a complete reimplementation in JavaScript, HTML, and CSS that replicates the behavior from scratch: the same markdown input, the same sticky-header stack, the same slide model, and the same animation timings. A deck that reads well in the terminal reads well on the web, because the rules are the same rules — but the code behind them is not.

Reimplemented

The behavior

The markdown parser, the header stack, the slide model, and the longest-common-prefix diff that makes persistence free — all rebuilt in JavaScript to match the terminal engine's output.

Added

Custom themes

Because the port renders to the DOM, it can do something the terminal cannot: swap in custom themes. The behavior is the same; the skin is yours.

A note on documentation: the web port is intentionally undocumented in the TUI manual, which describes the terminal tool and nothing else. If you are looking for the browser version, the manual will not mention it. This page is the entry point.

Archaeology

PoorerPoint is the third version of the idea. The first two are worth recording, because the difference between them and this one is the whole point.

asciishow

The first. A curses program with a custom DSL. Every deck opened with a settings block, then !CONTENT!, then commands: !slide, !label, !wait, !center, !indent. You could place text at absolute coordinates, choose per-command animation speeds, and type a title character-by-character at 100 fps.

It was more expressive than what came after, and that was exactly the problem: it had one speaker. A private language is a private language.

PoorerPoint.py

The second. Same DSL, finally named. Still no model of a slide — persistence was achieved by not clearing the curses window, the same trick PowerPoint makes you do by hand. It worked, and it was forgotten, by its own author, within a few years. A private language dies with the mood that invented it.

PoorerPoint

This one. It replaced the DSL with markdown, deleted every layout command, and added exactly one thing the predecessors never had: a data structure. Slide { stack, anim, blocks }. Everything else is a rounding of what was already there.

The first two were written at 2pm on the patio of the cheapest hotel in Managua, half a drink in, annoyed at a subscription fee. That is the whole origin story. It is not a dramatic one. It is, on reflection, the correct one.

Install and run

Requires a Rust toolchain and a terminal that speaks UTF-8.

Design notes

Timing

The title block takes 333 ms total, with lines staggered so the last lands at 333. Content appears one block every 55 ms, starting at 333. The frame rate is 60 fps. These numbers are not tuned to be noticed. They are tuned to be finished before the audience starts waiting.

State

The engine holds a Vec<Slide>. Each slide carries its own title-stack snapshot and the list of lines introduced by that slide — a longest-common-prefix diff against the previous one. Animating that diff is what makes persistence free. Unchanged lines were never re-entered, so they never needed to be re-hidden.

Wrapping

Wrapping is by whitespace everywhere. No mid-word breaks. Tables are the one exception, and only when a single word is longer than its column can possibly be.
