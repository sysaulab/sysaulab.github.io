Fuzzy search without the full scan.

A character-presence bitmask filter that narrows the candidate set before any similarity score is computed. Bucket words by which characters they contain, then look up the buckets that could possibly match.

What it is

Fuzzy string matching is what happens when you type helo and expect hello to come back. It is the machinery behind spell checkers, search autocomplete, command-line fuzzy finders, and duplicate detection.

The expensive part is the scoring. Every candidate word has to be compared to the query with some similarity metric — edit distance, Jaro-Winkler, subsequence matching. If your dictionary has a million words, you do not want to score all million.

fuzzy_dict is a pre-filter. It throws away most of the dictionary before any scoring happens, using a cheap necessary condition: if a candidate lacks a character class that appears in the query, it probably cannot match.

The core idea: give every word a 64-bit fingerprint of which characters it contains. Bucket words by that fingerprint. At query time, look up the exact bucket plus a handful of neighbours. Only score what survives.

It is a first-stage candidate collector, not a complete matcher. It does not compute edit distance. It does not replace a similarity metric. It makes the metric cheaper by giving it less work to do.

How it works

Each word gets a 64-bit mask. Every bit represents a character class — a group of characters that are treated as equivalent. Bit 1 might mean "a, A, á, À, â, Ä, ã, Ã", bit 2 might mean "b, B", and so on. Bit 0 is reserved for characters the alphabet does not know about.

For a word, you set the bits for every character class it contains. hello sets the bits for h, e, l, o. world sets w, o, r, l, d. The mask is order-blind: it records which classes are present, not where.

The search

At query time, the algorithm computes the query's mask and then looks up not just the exact bucket, but every bucket whose mask differs by one or two bits. The reasoning is straightforward: a candidate that is missing one character from the query might still be a good fuzzy match. A candidate missing two might too. A candidate missing five is probably not worth scoring.

The expansion is bounded. There are at most 64 bits to consider, so the number of masks generated is constant in the dictionary size. Most of those masks correspond to empty buckets, so the actual lookups are few.

Candidates from the surviving buckets are scored with a small inline function. Collection stops early once the running score sum crosses a threshold, and if a word in the exact bucket scores a perfect 1.0, it is returned immediately as the sole result.

Alphabet handling — read this first

The alphabet is defined by plain text files, one character class per line. Characters on the same line share a bit, which is how you get case-insensitivity and accent-insensitivity for free. Group aAáÀâÄãÃ on one line and they all become the same class.

When multiple alphabet files are loaded, they are merged line-wise: line 0 from every file shares bit 1, line 1 shares bit 2, and so on.

This is the biggest gotcha in the library. Load Latin and Cyrillic together, and the Latin a and the Cyrillic А both land on line 0 of their respective files. They share a bit. They are treated as the same character.

The default alphabet — Alphabet::default() — loads every standard alphabet merged this way. It is convenient for demonstrations and unsuitable for anything else.

What to do instead

Load only the scripts you actually need: 

let alphabet = Alphabet::load_named(&["latin"]);
let alphabet = Alphabet::load_named(&["cyrillic"]);
let alphabet = Alphabet::load_named(&["latin", "symbol"]);

If you need strict separation between scripts, use a separate dictionary per script and merge the results yourself. The library does not do it for you.

Included alphabets

The assets/ directory ships with definitions for scripts across Europe, the Caucasus, the Middle East, South and Southeast Asia, Africa, the Americas, and Central and East Asia. There is also a symbols file.

Mongolian is currently broken. The file contains # comment lines, and the loader does not skip them — it treats them as character classes. Clean up the file or patch the loader if you need Mongolian.

CJK

Chinese, Japanese, and Korean are logographic. They have thousands of characters and cannot fit in a 64-bit mask. The library does not romanise. If you want to filter CJK text, romanise it in your application — pinyin, romaji, whatever fits — before passing it in.

Usage

Not yet on crates.io. Depend on it from git: 

[dependencies]
fuzzy_dict = { git = "https://github.com/yourusername/fuzzy_dict" }

A complete example:

use fuzzy_dict::{Alphabet, FuzzyDict};

fn main() -> Result<(), Box<dyn std::error::Error>> {
    // Load only the script you need.
    let alphabet = Alphabet::load_named(&["latin"]);
    let mut dict = FuzzyDict::with_alphabet(alphabet);

    // Load a dictionary file (one word per line, '#' for comments).
    dict.add_file("dictionary.txt")?;

    // Or add words manually.
    dict.add_word("hello");
    dict.add_word("world");

    let results = dict.search_limit("helo", 10);
    for (word, score) in results {
        println!("{} -> {:.3}", word, score);
    }

    Ok(())
}

Scoring

The scorer is small and fast. It compares the longest common prefix and the longest common suffix of the two strings, then normalises and caps the result: 

score(a, b) = min( (LCP(a,b) + LCS(a,b)) / max(len(a), len(b)),
                   min(len(a), len(b)) / max(len(a), len(b)) )

The second term is a cap. Without it, a short string fully contained in a longer one — cat inside category, say — could score a perfect 1.0.

Byte-length scoring. The implementation currently uses str::len(), which counts bytes, not characters. For non-ASCII scripts this halves scores and distorts ranking. The fix is a one-line change to chars().count(), but it is not applied.

The scorer is also not pluggable. If you want Jaro-Winkler, Levenshtein, or a custom metric, you have to edit the source. There is no trait or function pointer to swap in.

Limitations

This is a weekend project. It is open source and usable, but the caveats below are real and worth reading before you rely on it.

Limitation Impact
Default alphabet merges all scripts Cross-script characters collide on the same bit. The biggest gotcha in the library.
Byte-length scoring Non-ASCII ranking is distorted. Halves scores for Cyrillic, Greek, Arabic, and others.
False negatives for query-only characters A query containing a character that appears nowhere in the dictionary can miss valid matches.

Scorer not pluggable Changing the metric requires editing the source.
No test suite No unit or integration tests. This is a prerequisite for a stable release.

The false negative condition

The filter is designed to never miss a potential match — that is what makes a pre-filter useful. But there is one case where the current implementation breaks that guarantee.

When expanding from the exact mask to neighbouring masks, the algorithm only flips bits that appear somewhere in the dictionary. If the query contains a character that appears nowhere in the dictionary, that bit is set in the query's mask but is not in the dictionary's effective mask. No flip ever turns it off, so the search cannot reach any bucket whose mask lacks it — even though every dictionary word lacks it.

The fix is one line: compute the set of flippable bits as effective_mask | query_mask. Until that is applied, the "no false negatives" claim does not hold for queries containing characters absent from the dictionary.

Alphabet loader quirks

The loader skips empty lines but does not skip # comments. It uses the raw line index for bit assignment, so blank lines leave gaps in the bit range. It trims whitespace from each line, which means whitespace characters cannot be defined as a class — the symbols file loses its space and tab.

Where it sits

Fuzzy matching has a lot of prior art. The bitmask filter is not trying to replace any of it — it is trying to make it cheaper by reducing the candidate set first.

Complementary

SymSpell

Pre-computes symmetric deletions for edit distance up to 2. The bitmask filter can reduce the candidate set passed to it.

Different trade-off

BK-trees

Traverse a metric space and prune on distance bounds. O(log n) traversal versus constant-time candidate collection, but they capture more information.

Order-aware

N-gram filters

Capture character order but require more storage and more complex query processing. The bitmask trades order for compactness and speed.

Probabilistic

Bloom filters

FlashFuzzy uses them for pre-filtering. This approach is deterministic, not probabilistic.

The bitmask idea itself is not new. Fuzzysort uses a 32-bit flag scheme for lowercase letters, digits, ASCII, and non-ASCII. This library generalises that to arbitrary alphabets and multiple scripts via configurable bit assignment.

Performance

Earlier versions of the README quoted specific throughput numbers — "100,000+ queries per second", "80–95% candidate reduction". Those have not been benchmarked reproducibly and depend heavily on the alphabet, dictionary, and query. They have been removed.

What can be said structurally:

  • Exact mask lookup is O(1) on average.
  • Expansion is bounded by the number of effective bits (≤ 64), so it does not grow with dictionary size.
  • Only candidates in matching buckets are scored.
  • Memory overhead is one mask per bucket, not per word — shared masks amortise.

On the "8 bytes per word" claim: that was inaccurate. The mask is stored once per bucket, and the real overhead depends on the bucket distribution. The hash map entry itself often dominates.
