Project Retrospective

A CMS that ran in the browser before the browser could fetch.

In 2002 there was no XMLHttpRequest. A page could not ask the server for data. This project compiled every fragment of a site — header, menu, content, footer — into a script, and let the browser's parser assemble the page. The result was a content management system that ran entirely on the client, routed by a query string, and cached fragment by fragment.

What it was

The problem was ordinary: a site has parts that repeat — a header, a menu, a footer — and one part that changes — the content. The usual answers in 2002 were server-side includes, CGI, or framesets. Server-side includes required a server that supported them. CGI required a process. Framesets required giving up bookmarks, the back button, and any hope of a clean URL.

This project took a fourth route. Instead of assembling the page on the server, it compiled each fragment into a JavaScript file — a JSS, for JavaScript Stream — whose only job is to write its own markup into the document. A small loader in the page read the query string and emitted the script tags in order.

The core idea: the browser already knows how to fetch and execute scripts. If every fragment of a page is a script, then the browser's own parser becomes the include mechanism, the scheduler, and the cache — with no server involvement beyond serving static files.

The author was Sylvain Saucier, and the code was written in C++ as a command-line compiler called html2jss: point it at a fragment, get a JSS back. The project is dated 2002 and released under a BSD 3-clause licence.

How it worked

The loader was a handful of lines. It read the query string, chose the content fragment, and wrote four script tags. The order was explicit, because the author wrote it that way: 

<script>
  var page = location.search.slice(1) || "home";
  document.write('<script src="header.jss"><\/script>');
  document.write('<script src="menu.jss"><\/script>');
  document.write('<script src="content/' + page + '.jss"><\/script>');
  document.write('<script src="footer.jss"><\/script>');
</script>

Each JSS was a stream of document.write calls. The header script wrote the header markup, the menu script wrote the menu, and so on. A fragment could itself emit more script tags, so the include tree could nest. The name “stream” was literal: the page was assembled as a sequence of writes, not as a single monolithic document.

It worked for a reason that has since disappeared. In IE3, Netscape 3, and the browsers that followed them, an external script was synchronous and blocking. The parser stopped, fetched the file, executed it, and only then continued. A document.write issued during parsing was spliced into the token stream and executed in place. Ordering was free. There were no callbacks, no promises, no state machine — the parser was the orchestrator.

The one sharp edge was escaping. Any </script> inside the emitted markup had to be written as <\/script>, or the parser would end the outer script early. That is the kind of detail a compiler exists to handle, and presumably html2jss did.

The caching behaviour fell out for free. Header, menu, and footer were the same files on every page, so the browser cached them once and reused them. Only content/<page>.jss changed. That is fragment-level caching with a query-string router — the same shape as a modern edge-side include, minus the edge.

The toolkit

The project was small and conventional for its time: a C++ compiler, a loader, a fragment layout, and a set of install scripts for the Windows platforms of the day.

Compiler

html2jss

Takes an HTML fragment and emits a JSS: a script that writes that fragment back into the document. C++, command-line, one job per invocation.

Loader

The page shell

A small inline script that reads location.search, chooses the content fragment, and writes the four script tags in order.

Layout

Header, menu, content, footer

Four JSS fragments per page. The first three are shared and cached; the fourth is selected by the query string.

Install

Platform scripts

Batch files for the Windows platforms of 2002 — Win95 through XP — wrapping the compiler invocation for the local toolchain.

Where the design met its edges

The architecture was coherent, but it had a narrow set of assumptions, and each one is a boundary worth naming.

Silent failure

A missing fragment was a 404 on a script tag, and a 404 on a script tag is silent. The page rendered with a blank region and no error. There was no error surface unless the compiler emitted a fallback write, and there was no way for the loader to know which fragment had failed.

One shot only

document.write after the document has finished loading wipes the page. The design was therefore strictly one-shot: the loader had to run during parsing, and nothing could be reloaded dynamically afterwards. That was acceptable in 2002 and is incompatible with how pages are built now.

Invisible to crawlers

Search engines of the era did not execute scripts. A site built this way was, to a crawler, an empty page with a few script tags. The content existed only for browsers that ran JavaScript.

Ordering by accident

The four fragments assembled in the right order only because script loads were synchronous and blocking. Add async or defer — or move to a browser that treats script loading differently — and the guarantee disappears. The design depended on a parser behaviour that was never promised to last.

The shared lesson: in each case, the browser was not a passive renderer. It had a fetch model, an execution order, and a caching policy — and the design lived or died on the exact shape of those guarantees. The interesting failures live at the boundaries.

What this is — and what it is not

This is a historical artifact and a demonstration of an idea. The concept — client-side composition from cached fragments, routed by a query string — survives in modern form as ES modules, dynamic import(), and fragment-level caching. The implementation does not survive as a recommendation: document.write is the wrong tool today, and the browser guarantees it relied on are gone.

The source itself needs work before it will build again. The files are encoded in Windows-1252 rather than UTF-8 — the French comments carry the accented bytes that break a modern decoder — and they need conversion before a current compiler will read them cleanly. The build scripts reference html2jss.cc, but the source file is html2jss.cpp, so the invocation as written would not find its input.

Two of the install scripts — win32-gcc.bat and win32-bcc32.bat — are byte-identical. The second was evidently copied from the first and never edited, so the Borland build path is a placeholder rather than a working script. The documentation folder promised by the README is not present in the recovered tree.

The honest summary: the idea was sound for its moment, the implementation was small and direct, and the constraints that made it work are exactly the constraints that make it unwise now. That is not a criticism. It is what a decade looks like in software.
