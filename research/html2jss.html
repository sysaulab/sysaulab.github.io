Project Retrospective

The query string was the file path.

The JavaScript Stream loader had no router table and no URL rewriting. It had a string, a rule about length, and a parser that counted characters. Every two characters were a directory; the last three, if the length was odd, were a file. The scheme was compact, trivial to implement, and — in ways that would not have a name until a decade later — hostile to search engines on almost every layer.

What the scheme was

The loader read location.search — everything after the ? — and sliced it into two-character segments. If the total length was even, every segment was a directory, and the file was the default index.jss. If the length was odd, the last three characters were the file name, and every pair before them was a directory. One character of parity decided the structure of the whole path.

Query Length Segments Resolves to
?en 2, even en /en/index.jss
?fr 2, even fr /fr/index.jss
?enwe 4, even en, we /en/we/index.jss
?enadd 5, odd en, file add /en/add.jss
?enweadd 7, odd en, we, file add /en/we/add.jss
?enwefoob 8, even en, we, fo, ob /en/we/fo/ob/index.jss

The examples make the rule clear. ?enwe loads the index of the en/we directory. ?enweadd loads add.jss from the same directory. The difference between “a directory” and “a file” is one character of length — and the difference between the two URLs is three characters at the end.

The core idea: the query string is not a set of key-value parameters. It is a path, compressed two characters per segment, with a parity bit at the end to say whether the last segment is a directory or a file. The router is not a table. The router is arithmetic on the string's length.

How it parsed, and why it existed

The parser was a handful of lines. Strip the ?. Check the length modulo 2. If even, walk the string in pairs and emit a directory for each; append index.jss. If odd, walk all but the last three in pairs; take the last three as the file name; append .jss. Then write the script tag. There was no URL decoding, no query-string parsing, no key-value splitting, no escaping. The string was the path.

The scheme existed because the alternative was expensive. In 2002, path-based routing meant server configuration — rewrite rules, mod_rewrite, custom 404 handlers — or a server-side script that generated the loader HTML per request. The project was static files on a static host. A query-string router that ran entirely in the browser meant the server never had to know the site's structure at all.

It also made the loader identical for every URL. One HTML file, one inline script, one set of fragment files. The server served one shell and a tree of .jss files. The client assembled the page. That is the whole architecture, and the URL scheme was the smallest possible router that could express it.

The parity trick is genuinely clever. It encodes two different path shapes — “directory path with default file” and “directory path with explicit file” — into a single string, with one bit of information (the length modulo 2) distinguishing them. No separator, no extension, no reserved character. Just count the characters.

The grammar that fell out is tighter than it first appears. Directory names are exactly two characters — not “up to two.” File names are exactly three characters, or the default index. That rules out a great many names: ?enwefile does not load file.jss from en/we; it loads le/index.jss from en/we/fi, because eight is even. To get a file called file, you would need it to be three characters, or you would need to treat it as a directory and serve file/index.jss — which the parity rule then forbids, because file is four characters and a directory segment is two. The scheme is a tiny filesystem with fixed-width names, and every name outside the width is unreachable.

Why it was hostile to search engines

In 2002, search engine optimisation was not yet a field with a name. Google was four years old. The vocabulary for describing why a site was uncrawlable — client-side rendering, duplicate content, canonical URLs, per-page metadata — did not exist. The project was not failing at SEO. It was failing at problems that would later be given SEO names. It was unfriendly on every layer at once.

One shell, every URL

The server returned the same HTML for every query string. The loader was inline, the fragments were fetched by script tags, and the page source contained no content — only the loader. A crawler fetching ?en, ?fr, ?enwe, and ?enweadd received identical bytes four times. That is the purest form of duplicate content: not similar pages, but literally the same page, distinguished only by a string the server never saw.

Crawlers did not run JavaScript

No major crawler in 2002 executed JavaScript. The content existed only after the loader ran and the fragments loaded. To a crawler, the site was an empty HTML shell with a script tag. Every page on the site was empty in exactly the same way.

Query strings were demoted or ignored

Crawlers of the era treated ? as a signal of dynamic content — session IDs, tracking parameters, search results — and many either ignored query-string URLs entirely or ranked them lower. The scheme was built on the assumption that the query string was the only thing a static host could vary. That assumption was correct for the host and fatal for the crawler.

No per-page title or metadata

The shell had one <title> for the whole site. There was no per-page title, no description, no keywords, no headings that varied by URL — because the HTML did not vary by URL. Even a crawler that somehow reached the content would have found no metadata to index it under.

No descriptive URLs

Two-character directory segments carry no keywords. ?enweadd does not read as “add a page in English, Western Europe section.” It reads as eight characters. Even if a crawler had indexed the URL text, there was nothing in it to index. The same is true for anchor text: every link on the site was a query string, so the link graph — the thing crawlers use to understand what a page is about — carried no information at all.

No crawlable site structure

A crawler builds a map of a site by following links. Here, links were query strings pointing at script files that assembled pages the crawler could not execute. The “site” as a graph did not exist. Each URL was an island with no content and no outgoing links the crawler could follow.

No status signal for missing content

A missing fragment was a 404 on a <script> tag, and a 404 on a script tag is silent. The page URL itself always returned 200, because the shell always existed. The server had no way to say “this page does not exist,” and the browser had no way to surface it. A crawler could not distinguish a valid URL from an invalid one — both returned the same shell with the same status.

Parity was invisible to humans

This one is not a crawler problem but a usability problem that compounded it. ?enwe and ?enweadd differ only in length. Nothing in the URL visually signals whether it points at a directory or a file. A human sharing a link had to trust that the character count was right; a typo of one character silently changed the target from /en/we/add.jss to /en/we/ad/d/index.jss or to a 404. The encoding was compact and the parser was trivial, but the URL did not explain itself.

The shared lesson: every layer of the scheme was optimised for the constraints of 2002 — static hosting, no server routing, no XMLHttpRequest, no JavaScript execution in crawlers. Each optimisation was correct for its constraint. Each one also removed a signal that search engines would later depend on. The scheme did not fail at SEO. It succeeded at a different problem, and the cost was paid in a currency that did not yet have a name.

What this is — and what it is not

This is a compact, working URL scheme for a client-side include system. It encoded a directory tree in a query string with two characters per segment, one bit of parity, and no server involvement. The parser was a few lines. The scheme was unambiguous. For the architecture it served — static fragments, client-side assembly, no server routing — it was exactly enough.

It is also the earliest form of a problem that would be named a decade later. A single-page application with client-side routing, query-string URLs, no server-side rendering, and no per-page metadata has the same crawlability problems this scheme had. The modern solutions — server-side rendering, prerendering, hydration, the History API, canonical URLs, per-route metadata — all address the same underlying issue: a crawler that does not execute the client's code sees the same empty shell for every URL. This project ran into that wall in 2002, before the wall had a name.

It is not, and was never meant to be, a search-friendly scheme. The project was a CMS for a static host, built by someone who wanted fragment-level caching and bookmarkable URLs without a server. It got both. The cost was every signal a search engine would eventually need, paid before anyone was keeping score.

The honest summary: the URL scheme was a small, correct solution to the problem it was built for. It was SEO-unfriendly on nine distinct layers, and it predated the field by enough that no one could have told you which nine. That is not a criticism of the design. It is what building for the constraints in front of you looks like when the constraints later change.
