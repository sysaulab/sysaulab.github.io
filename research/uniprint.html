Research Overview

Terminals do not know how wide their own glyphs are.

A modern emoji renders differently across terminals, and its cursor advance differs too. Across eleven terminals on two operating systems, the share of graphemes whose measured width disagrees with unicode-width ranges from 0.25% to 64.27%. The lowest count is not always the best terminal — two of the terminals we tested report correct cursor positions while rendering decomposed glyphs.

What is this about?

A terminal is, in principle, a grid of fixed-width cells. A program writes a sequence of bytes; the terminal advances the cursor by the number of cells that sequence visually occupies. This contract has held for ASCII for fifty years. It has not held for Unicode for the last twenty.

The failure is not confined to obscure codepoints. Emoji are among the most frequently emitted non-ASCII characters in interactive software. The sequence 🏌🏼‍♀️ (U+1F3CC U+1F3FC U+200D U+2640 U+FE0F) renders as a single image in every major terminal. It is measured differently in every one. Some terminals report two cells. Some report five. Some report seven.

The core problem: applications lay out text on the grid using the cursor model, not the visual. If the terminal's reported advance disagrees with its rendered glyph, every layout that follows drifts. The user sees broken borders, misaligned boxes, and stray half-glyphs.

Unicode defines grapheme cluster boundaries in UAX #29 and character width via East Asian Width (UAX #11). Neither was designed for how terminals use them. The first is a segmentation property; the second is a per-codepoint legacy table. Nothing in the standard defines the width of an extended grapheme cluster.

How we measure

We measure the terminal's cursor advance using the standard Cursor Position Report sequence. The technique is not new — the ucs-detect tool has used it for years — but applying it to the full Unicode emoji corpus, per terminal version, and aggregating the results into a shareable profile, is the part we believe has not been done systematically.

The probe enters the alternate screen, disables autowrap, and puts the terminal into raw mode with a short read timeout. For each grapheme cluster of interest:

  1. Move the cursor to column 1 of a reserved row.
  2. Write the grapheme.
  3. Send ESC [6n and read the reply ESC [<row>;<col>R.
  4. The measured advance is col - 1.

Our corpus is the fully-qualified set from emoji-test.txt (Unicode 16.0) plus the ASCII printable range for baseline verification — 4,058 sequences in total, including the unqualified entries. Each sequence is segmented with a UAX #29 implementation; we require exactly one cluster per fully-qualified emoji to validate the segmentation library. The expected width is the sum of per-codepoint widths according to unicode-width, which implements UAX #11. We report deviation = measured - expected.

Terminals, two platforms

Per-probe time varies across more than two orders of magnitude, and the variation is not correlated with correctness. The fastest terminal — Terminal.app at 0.06 ms — is also the second-worst by deviation rate. The slowest — Kitty on Debian at 29.43 ms — sits in the middle of the Linux group. Three of the Linux terminals, all VTE-based, report a per-probe time of exactly 16.67 ms, one frame at 60 Hz; their CPR response appears to be coupled to the screen refresh rather than the input loop. Alacritty and Konsole respond in a tenth of a millisecond, without waiting for a frame.

All Linux terminals were tested inside an Apple hypervisor VM running Debian 13.7 with the XFCE4 desktop. Absolute per-probe times are inflated by virtualisation and are not directly comparable to the bare-metal macOS figures; comparisons within each platform are valid. The corpus is identical across platforms. The base Debian install ships without a colour emoji font, so the first Linux pass measured the terminals against a stock font stack — a monochrome fallback and whatever else fontconfig could resolve. zA second pass was run on four of the seven Linux terminals after installing Noto Color Emoji, to isolate the effect of font coverage from the effect of the terminal binary. Those results appear in the findings. As a control, we also measured the kernel's own virtual console — not a terminal emulator at all, but the driver that underlies every one of them on Linux. It is the fastest subject in the study and the least correct.

What we found

The distribution is wide and is not structured by terminal architecture. The best result — Kitty on macOS, at ten deviations in 4,058 sequences — is nearly two orders of magnitude better than the next best, iTerm2. The worst — Hyper at 64.27% — is barely worse than the most common result on Linux, a cluster of four terminals tied at exactly 61.51%.

The same binary, two versions, two platforms

The most striking comparison is Kitty against itself. On macOS 0.49.2 it deviates on ten sequences out of 4,058. On Debian 0.41.1, against the same corpus and the same width library, it deviates on 1,631. The version gap is eight minor releases — Debian stable is deliberately conservative — and the deviation gap is a factor of 163.

A follow-up pass installed Noto Color Emoji on the Debian VM and re-ran the measurement. The per-probe time fell from 29.43 ms to 12.59 ms, a 2.3× speedup: the terminal was no longer searching for a glyph it did not have, on every paint. The deviation count did not move. It was 1,631 before the install and 1,631 after, to the sequence.

This isolates the two properties the earlier draft had run together. The cursor advance the terminal reports is a property of its own Unicode tables, and those tables change with the binary version. The glyph the terminal paints is a property of the font stack. They are independent variables, and a terminal can be wrong on one while being right on the other — Kitty on Debian is wrong on the advance and, after the font install, correct on the paint. Kitty on macOS is correct on both.

The four-way cluster

Four Linux terminals report exactly 2,496 deviations: xfce4-terminal, GNOME Terminal, Alacritty, and Terminator. Three of the four are VTE-based; Alacritty is a Rust terminal written from scratch, with no shared lineage. That four such different programs agree to the sequence suggests the failures are being driven by something they consult in common rather than something they each do — the font stack, in short. We have not yet isolated font from terminal by holding one fixed while varying the other, and until we do, the cluster should be treated as evidence about the environment, not about the terminals inside it.

The near-neighbour is xterm, at 2,489 — seven sequences different, in the same direction. xterm has no emoji support at all, and no colour emoji font on this system was made available to it; the small gap from the VTE group likely reflects those seven sequences alone.

The font stack is necessary but not sufficient

Installing Noto Color Emoji on the Debian VM changed four things and left four things unchanged. Konsole gained colour rendering: ZWJ sequences that had been visibly decomposed became composed. Kitty's per-probe time dropped by more than half. Those are the changes. Kitty's deviation count was identical before and after. Konsole's deviation count was identical before and after. And xfce4-terminal and Alacritty were unchanged in both respects — their rendering did not improve either.

The reading is that the advance and the paint are separate observables. The advance is a width-table lookup inside the terminal and is not affected by which fonts are installed. The paint is a font-resolution problem and is affected by nothing else. A terminal that reports the standard's width and paints the standard's glyph is correct. One that paints correctly and reports wrongly is Mode A or B. One that reports correctly and paints wrongly is Mode D. And one that is unchanged by the presence of a colour font it should be using is a different failure entirely.

That two of the four terminals we re-tested picked up the font and two did not suggests the fallback chains differ. Kitty and Konsole resolve a newly installed colour font at runtime. The VTE-based terminals and Alacritty did not, even after restart, which points to a fallback path that does not consult a colour font when one becomes available. That is a third class of defect — one that a package dependency would not fix — and we have not isolated it further.

Speed and correctness

The fastest terminals in the study are the least correct. Everything under 0.15 ms per probe — the Linux virtual console, Terminal.app, xterm, Alacritty, and Konsole — has a problem. Four of the five deviate on 60% or more of the corpus. The fifth, Konsole, reports correctly and, before the font install, painted incorrectly. None of them is doing honest work in the cursor-position path.

The correlation is not a tradeoff between speed and accuracy as such. It is a consequence of what the cursor-position response consults. A terminal that answers in 0.06 ms has not looked at the grapheme — the reply has to come from a cursor model that was already sitting at the last cell boundary, and that model is by construction the terminal's internal width table, which for these terminals predates cluster awareness. Kitty on macOS, at 1.57 ms, is fast enough not to be frame-coupled and slow enough to have consulted a real table. It is also the most correct terminal we tested, by a factor of 163. Fast and correct is possible. Sub-0.15 ms is a different regime.

The VTE group's 16.67 ms deserves a note of its own: that is exactly one frame at 60 Hz. Those terminals appear to defer the cursor-position reply to the next screen refresh. The answer is then honest but late, and its 61.51% rate is a font-stack result rather than a cursor-path result.

Terminal.app and the Linux virtual console — 0.06 and 0.07 ms, 61.19% and 67.74% — are the two extremes of the fast-and-wrong regime. We cannot tell from the outside whether the speed is a deliberate battery optimisation or a downstream consequence of a CPR path that never consulted the renderer. Both explanations are consistent with the data; only one of them implies a choice.

Konsole and Hyper: the failure the probe cannot see

Konsole reports cursor positions that match what unicode-width predicts for most of the corpus, including ZWJ sequences, yet renders ZWJ sequences as visibly decomposed fragments. The probe sees a compliant terminal; the user sees a broken emoji. Hyper exhibits the same pattern. For both terminals the deviation count is a lower bound on the true failure rate.

Konsole's Mode D was resolved by the font install. Before Noto Color Emoji was present, the terminal advanced correctly and painted decomposed fragments; after, it advanced correctly and painted composed glyphs. Its deviation count was unchanged throughout, because the deviation count was never measuring the thing that was wrong. This is the cleanest example in the study of a Mode D failure that has nothing to do with the terminal binary and everything to do with the files it had to work with.

Hyper, whose macOS measurements are unaffected by any font experiment we ran, may be a different case: a terminal whose rendering layer structurally cannot compose a cluster the emulation layer has already decided to split across cells. Separating the two would require installing a colour font on the macOS side and re-measuring Hyper, which we have not done.

Konsole's 3.18% is the best Linux result in the table. It is also partly an artifact. We report the number because it is what the instrument produces; the caveat belongs beside it.

Mode A — measurement error

The terminal renders the cluster correctly — 2 cells wide on screen — but reports a cursor advance of 1. The visual is right; the cursor is behind. This is the dominant mode for VS16 sequences and single-codepoint emoji rendered in emoji presentation. It is what produces the -1 deviations.

Mode B — clustering error

The terminal sums the widths of the constituent codepoints. 🏌🏼‍♀️ becomes 2 + 2 + 0 + 1 + 0 = 5 (or 7, when the base codepoint has East Asian Width Wide and the modifier does too). The cursor advances by the sum. The visual may or may not match — in some terminals the composed glyph renders correctly and the cursor overshoots; in others the terminal decomposes the sequence and renders each codepoint separately. This is what produces the large positive deviations.

Mode C — the new-codepoint gap

Kitty's ten macOS deviations are all one class: the two base emoji 🫹 (U+1FAF9) and 🫺 (U+1FAFA), each paired with the five Fitzpatrick skin tones 🏻-🏿. Both sides of the measurement are stale. The width library's Unicode tables do not yet include the codepoints, so it falls back to summing per-codepoint widths and expects three cells. The terminal's font has no glyph for the base, so it renders the whole cluster in a single fallback cell and reports one. The deviation of -2 is not a correction either party needs to make; it is what a well-behaved terminal reports when it has not yet caught up with the standard, against a width table that has not either. These entries will disappear on their own once both the font and the Unicode tables catch up, and the padding the library applies in the meantime is sufficient to keep layout from drifting.

Mode D — rendering failure with a correct report

Konsole and Hyper report cursor positions consistent with unicode-width while rendering ZWJ sequences as separate visible fragments. The cursor advance and the visual disagree, but only the cursor advance is observable through CPR. No correction can be computed, because the report is already correct by the standard's own terms. This is the failure mode the probe is structurally unable to see, and it argues for a different kind of measurement entirely — one that observes the painted cells, not the reported cursor.

Capability is not uniform within a terminal, and not uniform across a platform. iTerm2 handles the family emoji 👨‍👩‍👧‍👦 correctly but mismeasures 🏌🏼‍♀️. Kitty handles both correctly on macOS but neither on Debian. A per-terminal boolean flag is insufficient; a per-terminal-version profile is insufficient; the deviation is per-cluster and the remedy is per-stack.

A note on input

iTerm2 and Terminal.app do not correctly produce a complex grapheme when the sequence is inserted through the macOS input widget (the fn key). Both fail to compose the full ZWJ cluster, emitting a fragment of the sequence instead. This is a separate failure mode from the width miscalculation — it is a defect in the path from the input method to the terminal, not in the terminal's layout logic — but it contributes to the same user-visible breakage. It is mentioned here because it argues against any solution that assumes well-formed clusters arrive at the terminal from the system.

A profile per delivery stack

The macOS results alone suggested a profile could be keyed on the terminal binary: every user of iTerm2 3.6.11 on macOS sees the same deviations, so the expensive calibration pass need only be performed once per terminal version and distributed. The Linux results complicate that conclusion. The same Kitty binary is near-perfect on one platform and 40% wrong on the other. The profile is not a property of the binary; it is a property of the stack the binary sits in.

Do once, distribute many times. The right unit is the delivery stack — terminal name, terminal version, OS family, and font stack. A profile for "Kitty 0.49.2 on macOS 26 with Apple Color Emoji" is shareable across every such installation. A profile for "Kitty on Linux" is not shareable across distributions, because the distributions do not agree on fonts.

The fingerprint

The profile is currently keyed on a deliberately coarse fingerprint: terminal name, terminal version, and OS family. It excludes TERM, LC_CTYPE, and window identifiers, which describe the session rather than the binary. The Linux results show this is too coarse in one direction — it does not distinguish the font stack — and too fine in another.

Too coarse on the font stack, because Kitty macOS and Kitty Debian share a terminal name and a version number scheme, and would collide on a profile if the OS family were not also part of the key. They are the same binary; they are not the same delivery system.

Too fine, because on Linux the TERM-based fallback collides across unrelated terminals. Alacritty only sets ALACRITTY_SOCKET when its IPC socket is enabled, and falls back to TERM when it is not — which on a default Debian desktop resolves to xterm-256color, the same value reported by several unrelated terminals. Two terminals that share a profile file will not each run their own calibration; one will inherit the other's results. We treat this as a bug to be fixed and not a property of the terminals, and note it here because any distributed profile system will face the same problem in some form.

Human review as a first-class artifact

A cursor-position probe reports the terminal's internal cursor model, not its visual rendering. When a terminal renders a glyph correctly but mismeasures it, the probe catches the error and a numeric correction can be applied. When a terminal renders a glyph incorrectly — decomposing a ZWJ sequence into visible fragments — the probe may or may not catch it, depending on whether the terminal's cursor model has been aligned to the standard or to its own paint. In the first case a human must decide; in the second, no numeric correction is possible at all.

Our implementation includes a review mode that walks every deviating entry, displays the suggested correction and its actual visual effect side by side, and allows the reviewer to accept, strip, or adjust. Reviewed entries are marked and are not re-presented in subsequent sessions. The output is a profile with two layers: what the terminal reported, and what a human decided was correct. Both are valuable; the second is authoritative. Review mode cannot repair Mode D failures, because those failures produce no entries to review.

The review workload tracks the deviation count, and the deviation count varies by two and a half orders of magnitude across the terminals we tested. Ten entries is an afternoon's curiosity; two and a half thousand is a substantial pass — but it is a pass that a single volunteer performs once for a given stack, and that every subsequent user of that stack inherits. The economics change when the result is shared.

Where the instrument fails

The cursor-position report cannot distinguish a terminal that renders correctly from one that renders incorrectly, if both report the same advance. A terminal that decomposes 🏌🏼‍♀️ into five visible glyphs and advances by five is self-consistent — the probe reports 5, the visual occupies 5 cells, no correction is needed, and the user sees garbage because the emoji did not compose. Konsole and Hyper demonstrate the inverse: they advance correctly and paint incorrectly, so the visual overflows into cells the cursor has already left.

No protocol-level query exists that reports how many cells the renderer actually painted. The DECRQCRA sequence — checksum a rectangular area — gets close, but was unsupported on all of the terminals we tested. It is not a portable solution.

The limits of user-space correction

A library that patches width at emit time can compensate for Modes A, B, and C on a per-stack basis. It cannot:

  • Correct a terminal that reports correctly and renders incorrectly, because no deviation is recorded to correct.
  • Communicate a grapheme's intended width to a terminal that has not been asked.
  • Prevent a terminal from decomposing a ZWJ sequence into visibly separate glyphs.
  • Handle line-breaking at grapheme boundaries if the terminal itself wraps mid-cluster.
  • Force a terminal's font stack to know about a codepoint it does not carry.

The eventual correct answer is a new standard and a reference implementation — a uniconsole that treats the grapheme cluster as a first-class layout unit and exposes it to applications through a negotiated protocol. Until that exists, empirical profiling is what works.

What a future standard should specify

  1. A negotiation handshake that reports the terminal's support level for extended clusters.
  2. A derived width property for grapheme clusters, computed once by the standard and implemented identically in every conforming terminal.
  3. Defined behaviour for cursor positioning within a cluster, line-breaking at cluster boundaries, and right-edge handling.
  4. A query interface by which an application can ask the terminal for a cluster's width without writing it, allowing layout to be computed before emit.
  5. A query interface for the rendered extent of a cluster — how many cells the terminal painted, as distinct from how many it advanced by — so that Mode D failures are observable at all.

The shared lesson: the terminal is not a passive substrate. It has a resolution, a semantic limit, and a guarantee that is narrower than it might appear. The interesting failures live at those boundaries — and the boundary between a grapheme cluster and a fixed-width cell is one of the least examined.

Conclusion

Modern terminals, even those shipping in 2026, do not uniformly measure extended grapheme clusters correctly. Across eleven terminals on two operating systems, the deviation rate ranges from 0.25% to 64.27%. The failure is per-cluster, not per-terminal; per-delivery-stack, not per-session. It cannot be worked around at the protocol level, because the protocol does not expose the information needed to distinguish a correct terminal from a consistently incorrect one — nor, in the case of Konsole and Hyper, a terminal that renders correctly from one that renders incorrectly while reporting the same number.

Our contribution is threefold. First, a methodology for characterising terminal behaviour using the standard cursor position report, applied to the full Unicode emoji corpus and validated across eleven terminals and two platforms. Second, a recognition that the deviations are properties of the delivery stack — terminal, font, platform — and are therefore shareable at a coarser granularity than the terminal binary alone; a profile system that centralises the expensive measurement so that most users never perform it. Third, a demonstration that some residual cases require human review, that others are invisible to the probe entirely, and that the second class motivates a different measurement.

The eventual correct answer is a new standard and a reference implementation. Until then, profiling is what works.
