Terminal Hex Viewer

Doesn't flinch at the theoretical limits.

A hex viewer built with 128-bit internals, demand-driven I/O, and SIMD-accelerated search. Tested against a 9 exabyte generative filesystem. It reads small config files and synthetic exabyte-scale streams with the same code.

What it is

A hex viewer shows you the raw bytes of a file — the actual numbers underneath the text, image, or executable. It is a low-level tool, used for inspecting file headers, debugging binary formats, and understanding what is really on disk.

Most hex viewers assume files fit comfortably within a 64-bit address space. That assumption is reasonable today: no mainstream filesystem exceeds 264 bytes. But the theoretical limits are larger, and synthetic filesystems can expose those boundaries for testing.

Hexwife was built to handle those theoretical maxima without compromise. Every offset, line number, and cursor position is stored and computed using 128-bit integers. The result is a tool that is mathematically correct up to 2128−1 bytes — and that stays lightweight while doing it.

The core idea: the viewer never assumes it knows how big the file is. Offsets are 128-bit, I/O is demand-driven, and the layout adapts to whatever the terminal and the file can support.

Design

Hexwife is a single-file Rust application built on ratatui and crossterm for the terminal interface. The design principles are simple, and each one is load-bearing.

Principle 1

No caching

Only the visible portion of the file is read, on every redraw. Memory usage stays constant, and the operating system's own page cache does the heavy lifting.

Principle 2

Dynamic layout

The number of bytes shown per line adjusts to the terminal width, respecting a user-selected grouping size. Nothing is hard-coded to a fixed column count.

Principle 3

Configurable grouping

Pressing 1–4 changes how bytes are clustered in the hex display, and the word interpretation below the cursor switches between u8, u16, u32, and u64 — in both little- and big-endian.

Principle 4

Scrollbar and mouse

A vertical scrollbar shows position within the file. The mouse wheel moves the cursor one line at a time. The scrollbar thumb reflects true progress, even at exabyte scale.

Because the viewer reads only what is visible, the memory footprint does not grow with file size. Opening a 9 exabyte file costs the same memory as opening a 9 kilobyte one.

Why 128-bit?

A 64-bit unsigned integer can address up to 264−1 bytes — roughly 16 exabytes. That is an enormous number, and it is the ceiling that every ordinary file API assumes. But the ceiling is real: a tool that uses 64-bit offsets cannot even represent a position past it, let alone navigate to one.

Hexwife uses u128 for every value that has anything to do with file position:

  • File length — stored as a 128-bit value.
  • Cursor position — the byte offset of the cursor, in 128 bits.
  • First visible line index — the scroll position, in 128 bits.
  • Viewport byte range — the start and end of the visible region, in 128 bits.

All critical arithmetic — computing the starting offset of a line, advancing the search cursor, sizing the address column — is done with saturating 128-bit operations. Nothing wraps around silently.

The address column

The number of hex digits in the address column is computed from the file size itself: 

digits = floor(log16(file_size - 1)) + 2

The + 2 gives one digit of headroom. For a 9 exabyte file (9 × 260 bytes), that works out to 17 hex digits per address — wide enough to hold the offset of the last byte without truncation, and wide enough that the column never has to be resized mid-session.

Graceful degradation at the OS boundary. When I/O is required, the 128-bit offset is converted to a 64-bit u64 through a checked helper that returns None for anything beyond 264−1. Since no present operating system can seek past that boundary, the viewer treats those regions as empty — mathematically consistent, and free of panics.

On a 64-bit CPU, the compiler lowers u128 operations to pairs of 64-bit instructions. The overhead compared to native 64-bit arithmetic is minor — not enough to be worth measuring in practice.

The 9 exabyte test

To validate the tool at extreme scale, a 9 exabyte sparse file was created using a generative FUSE filesystem written in Rust. The filesystem does not store any data. It responds to read and seek calls by synthesising content on the fly, behaving exactly like a real file of that size would.

This is the only practical way to test at this scale. Nine exabytes of real storage is not something anyone has, but a filesystem that claims to be nine exabytes and generates bytes on demand is enough to exercise every address calculation the viewer performs.

The ETA story

The first tests used FUSE-T, a user-space FUSE implementation that avoids kernel modules. Its overhead was severe: a full scan of the synthetic file produced a search ETA of roughly half a million years.

Switching to MacFuse reduced the overhead by a factor of 100, bringing the ETA down to around 5000 years. That is still not practical — but it is a useful measurement, because it demonstrates that the bottleneck is entirely I/O bandwidth. The viewer's own logic is not what makes the scan slow.

The ETA is not a bug. It is the honest arithmetic of nine exabytes divided by a few hundred megabytes per second. A number that large is a sign the tool is telling the truth.

What was verified

  • Address column. The 17-digit column correctly displays offsets for all visible lines, even when scrolling near the theoretical end of the file.
  • Cursor navigation. Arrows, s and e for start and end, and u and d for page up and page down all work without overflow or truncation.
  • Search. Finding a known byte pattern placed at various offsets — including 1 GB and beyond — succeeds, thanks to block-overlap logic that prevents missed matches at block boundaries.
  • ETA scaling. The search ETA scales correctly: thousands of years for a full 9 exabyte scan, seconds for small searches.
  • Mouse and scrollbar. Wheel scrolling and the scrollbar track the viewport accurately, with the thumb position reflecting true progress through the file.

Search

Pressing / opens a prompt that accepts either a hex pattern or an ASCII string. The search reads the file in 16 MiB blocks and scans each block for the pattern.

The scanning itself uses the memchr crate, which dispatches to the CPU's wide vector instructions where available — AVX2 or SSE4.2 on x86-64, NEON on AArch64. This is what makes the search practical at all: on modern NVMe storage, the scan runs at roughly 2–4 GiB/s when the file is local.

Blocks overlap slightly, so a pattern that straddles a block boundary is not missed. A live ETA is calculated from elapsed wall-clock time and bytes scanned, and displayed while the search runs. It adapts to the actual I/O speed rather than assuming one.

Editing

Hexwife is not only a viewer. Pressing the spacebar enters edit mode on the hex value at the cursor. You can change a byte in place, then return to viewing.

The edit feature is deliberately minimal: change a value, move on. It is there for the cases where you need to flip a byte to see what happens — patching a header, testing a format boundary, inspecting the effect of a single change — without leaving the terminal or opening a heavier editor.

Editing is a convenience, not the point. The point is that the viewer can address any byte in a file up to 2128−1, and the edit simply writes to the byte the cursor is already on.

Performance

The decision to skip internal caching keeps the memory footprint constant at around 20 MiB — the UI and the search buffers — regardless of file size. There is no growing cache, no index, no state that scales with the file.

On the name

The project started as a pun. The name stuck. The internals did not become a joke.

What began as a small hex viewer accumulated a serious design decision — 128-bit addressing throughout — and then a serious test case: a synthetic nine exabyte filesystem used to verify that the design holds at the limits. The tool is small, auditable, and does one thing.

Simple hexadecimal viewer started as a pun. It internally uses 128-bit for display ranges and other related computations. Used to verify operating systems' compliance with very large files using generative filesystems capable of serving file content up to the limit. Or just for giggles.

The source is a single Rust file, small enough to read in one sitting. That is deliberate: a tool that makes claims about correctness at the limits should be easy to audit.
