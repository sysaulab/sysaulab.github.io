Research Overview

Terminals do not know how wide their own glyphs are.

A modern emoji renders identically across macOS terminals. Its cursor advance does not. This research measures the gap, proposes a shareable profile for each terminal version, and argues that nothing short of a new standard will close it.

What is this about?

A terminal is, in principle, a grid of fixed-width cells. A program writes a sequence of bytes; the terminal advances the cursor by the number of cells that sequence visually occupies. This contract has held for ASCII for fifty years. It has not held for Unicode for the last twenty.

The failure is not confined to obscure codepoints. Emoji are among the most frequently emitted non-ASCII characters in interactive software. The sequence 🏌🏼‍♀️ (U+1F3CC U+1F3FC U+200D U+2640 U+FE0F) renders as a single image in every major terminal. It is measured differently in every one. Some terminals report two cells. Some report five. Some report seven.

The core problem: applications lay out text on the grid using the cursor model, not the visual. If the terminal's reported advance disagrees with its rendered glyph, every layout that follows drifts. The user sees broken borders, misaligned boxes, and stray half-glyphs.

Unicode defines grapheme cluster boundaries in UAX #29 and character width via East Asian Width (UAX #11). Neither was designed for how terminals use them. The first is a segmentation property; the second is a per-codepoint legacy table. Nothing in the standard defines the width of an extended grapheme cluster.

How we measure

We measure the terminal's cursor advance using the standard Cursor Position Report sequence. The technique is not new — the ucs-detect tool has used it for years — but applying it to the full Unicode emoji corpus, per terminal version, and aggregating the results into a shareable profile, is the part we believe has not been done systematically.

The probe enters the alternate screen, disables autowrap, and puts the terminal into raw mode with a short read timeout. For each grapheme cluster of interest:

  1. Move the cursor to column 1 of a reserved row.
  2. Write the grapheme.
  3. Send ESC [6n and read the reply ESC [<row>;<col>R.
  4. The measured advance is col - 1.

Our corpus is the fully-qualified set from emoji-test.txt (Unicode 16.0), roughly 3,700 sequences, plus the ASCII printable range for baseline verification. Each sequence is segmented with a UAX #29 implementation; we require exactly one cluster per fully-qualified emoji to validate the segmentation library. The expected width is the sum of per-codepoint widths according to unicode-width, which implements UAX #11. We report deviation = measured - expected.

What we found

Across the two macOS terminals tested, the distribution of per-grapheme deviations is unambiguous. iTerm2 is more compliant but not correct. Terminal.app is dramatically less compliant.

Terminal Version Deviating sequences Worst deviation
iTerm2 3.6.11 339 −3
Terminal.app 2.14 (macOS 15) 2,483 +7

The distribution is bimodal. Negative deviations cluster at −1 and correspond to wide glyphs the terminal renders correctly but advances by one cell. Positive deviations are integers between +1 and +7 and correspond to ZWJ sequences where the terminal sums the widths of the constituent codepoints.

Mode A — measurement error

The terminal renders the cluster correctly — 2 cells wide on screen — but reports a cursor advance of 1. The visual is right; the cursor is behind. This is the dominant mode for VS16 sequences and single-codepoint emoji rendered in emoji presentation. It is what produces the −1 deviations.

Mode B — clustering error

The terminal sums the widths of the constituent codepoints. 🏌🏼‍♀️ becomes 2 + 2 + 0 + 1 + 0 = 5 (or 7, when the base codepoint has East Asian Width Wide and the modifier does too). The cursor advances by the sum. The visual may or may not match — in some terminals the composed glyph renders correctly and the cursor overshoots; in others the terminal decomposes the sequence and renders each codepoint separately. This is what produces the large positive deviations.

Capability is not uniform within a terminal. iTerm2 handles the family emoji 👨‍👩‍👧‍👦 correctly — it measures two cells, matching the visual — but mismeasures 🏌🏼‍♀️. A per-terminal boolean flag is insufficient. The deviation is per-cluster.

A note on input

Neither terminal correctly produces a complex grapheme when the sequence is inserted through the macOS input widget (the fn key). Both fail to compose the full ZWJ cluster, emitting a fragment of the sequence instead. This is a separate failure mode from the width miscalculation — it is a defect in the path from the input method to the terminal, not in the terminal's layout logic — but it contributes to the same user-visible breakage. It is mentioned here because it argues against any solution that assumes well-formed clusters arrive at the terminal from the system.

A profile per terminal version

The failure modes we measured are properties of the terminal binary, not of the user's session. Every user of iTerm2 3.6.11 on macOS sees the same deviations. This suggests that the expensive calibration pass — probing thousands of sequences at roughly twenty milliseconds each — need only be performed once per terminal version, and distributed.

Do once, distribute many times. A canonical repository of profiles, updated when new terminal versions ship and validated by anyone who runs the calibration, means that most users never run the probe. The library ships with a bundled snapshot and consults the live cache only when the running terminal's fingerprint is not covered.

The fingerprint

The profile is keyed on a deliberately coarse fingerprint: terminal name, terminal version, and OS family. It excludes TERM, LC_CTYPE, and window identifiers, which describe the session rather than the binary. A profile for "iTerm2 3.6.11 on macOS" is shareable across every iTerm2 3.6.11 installation.

Human review as a first-class artifact

A cursor-position probe reports the terminal's internal cursor model, not its visual rendering. When a terminal renders a glyph correctly but mismeasures it, the probe catches the error and a numeric correction can be applied. When a terminal renders a glyph incorrectly — decomposing a ZWJ sequence into visible fragments — the probe reports a value that is consistent with the (wrong) rendering, and no automatic correction is possible.

For those residual cases, a human must look at the terminal and decide. Our implementation includes a review mode that walks every deviating entry, displays the suggested correction and its actual visual effect side by side, and allows the reviewer to accept, strip, or adjust. Reviewed entries are marked and are not re-presented in subsequent sessions. The output is a profile with two layers: what the terminal reported, and what a human decided was correct. Both are valuable; the second is authoritative.

Two and a half thousand entries is a substantial review pass, but it is a review that a single volunteer performs once for a given terminal version, and that every subsequent user of that version inherits. The economics change when the result is shared.

Where the instrument fails

The cursor-position report cannot distinguish a terminal that renders correctly from one that renders incorrectly, if both report the same advance. A terminal that decomposes 🏌🏼‍♀️ into five visible glyphs and advances by five is self-consistent — the probe reports 5, the visual occupies 5 cells, no correction is needed, and the user sees garbage because the emoji did not compose.

No protocol-level query exists that reports how many cells the renderer actually painted. The DECRQCRA sequence — checksum a rectangular area — gets close but is unsupported on both of the terminals we tested. It is not a portable solution.

The limits of user-space correction

A library that patches width at emit time can compensate for both modes of error on a per-terminal basis. It cannot:

  • Communicate a grapheme's intended width to a terminal that has not been asked.
  • Prevent a terminal from decomposing a ZWJ sequence into visibly separate glyphs.
  • Handle line-breaking at grapheme boundaries if the terminal itself wraps mid-cluster.

The eventual correct answer is a new standard and a reference implementation — a uniconsole that treats the grapheme cluster as a first-class layout unit and exposes it to applications through a negotiated protocol. Until that exists, empirical profiling is what works.

What a future standard should specify

  1. A negotiation handshake that reports the terminal's support level for extended clusters.
  2. A derived width property for grapheme clusters, computed once by the standard and implemented identically in every conforming terminal.
  3. Defined behaviour for cursor positioning within a cluster, line-breaking at cluster boundaries, and right-edge handling.
  4. A query interface by which an application can ask the terminal for a cluster's width without writing it, allowing layout to be computed before emit.

The shared lesson: the terminal is not a passive substrate. It has a resolution, a semantic limit, and a guarantee that is narrower than it might appear. The interesting failures live at those boundaries — and the boundary between a grapheme cluster and a fixed-width cell is one of the least examined.

Conclusion

Modern terminals, including those shipping in 2025, do not correctly measure extended grapheme clusters. The failure is per-cluster, not per-terminal; per-terminal-version, not per-session. It cannot be worked around at the protocol level because the protocol does not expose the information needed to distinguish a correct terminal from a consistently incorrect one.

Our contribution is threefold. First, a methodology for characterising terminal behaviour using the standard cursor position report, applied to the full Unicode emoji corpus and validated on the two terminals available to us on macOS. Second, a recognition that the deviations are properties of the terminal binary and are therefore shareable — a profile system that centralises the expensive measurement so that most users never perform it. Third, a demonstration that the residual cases require human review, and a workflow by which that review is incremental, resumable, and produces a durable artifact.

The eventual correct answer is a new standard and a reference implementation. Until then, profiling is what works.
