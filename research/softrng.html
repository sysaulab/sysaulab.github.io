Research Overview

Randomness from the operating system itself.

Most computers get their randomness from specialised hardware. This research asks a different question: can you harvest it from the software that is already running — the scheduler, the timer, the way threads race for the CPU?

What is this about?

Every secure system needs randomness. Encryption keys, session tokens, nonces — they all depend on numbers that an attacker cannot guess. The usual way to get those numbers is from a dedicated hardware chip that measures physical noise: thermal fluctuations, quantum effects, electronic jitter.

This research explores a different approach. Instead of adding hardware, it harvests randomness from the operating system's own behaviour. When multiple threads compete for the CPU, the exact moment one of them gets to run is determined by a complex, unpredictable interaction of scheduling decisions, cache states, and run-queue dynamics. That unpredictability is the raw material.

The core idea: a thread that yields the CPU and then reads shared memory is sampling a decision that only the operating system's scheduler can make. That decision depends on the entire state of the machine — and it cannot be predicted from inside the process.

The research is documented across four connected papers, a toolkit of command-line programs, and a measurement methodology that treats the estimator as an instrument with its own limits.

How it works

The generator — called speedy64 — uses three threads that race on a shared ring of memory. Each thread repeatedly reads a value, transforms it, and writes it back. There are no locks, no synchronisation, no barriers. The threads genuinely compete.

The main thread is also the emitter. It mixes its part of the ring, then calls sched_yield() — asking the operating system to pause it and run something else. The scheduler decides when to bring it back. That decision depends on which other threads are runnable, on which cores, under what load, with what recent runtime accounting. None of that is visible to the process.

When the thread resumes, it reads all three ring nodes and XORs them together. The value it reads encodes how much the other two threads advanced during the yield — which encodes the scheduler's decision. A fixed mixing function spreads that tiny perturbation across all 64 bits of the output word.

The design requires two independent ingredients: a large state space (the racing ring) and an unpredictable sampling instant (the scheduler's decision). Neither alone is enough. The research demonstrates this with negative controls — variants that remove one ingredient and fail visibly.

Measuring randomness honestly

A common mistake in randomness research is to report a single number — "our generator achieves 7.12 bits of entropy per byte" — as if it were a property of the generator. It is not. It is a property of the generator as measured by a particular estimator, on a particular slice size, with a particular slice count, on a particular machine.

The methodology paper in this suite makes a simple argument: the dominant uncertainty in practical min-entropy measurement is the estimator itself, not the source. The estimator has a ceiling and a floor. A source whose numbers sit inside that envelope cannot be distinguished from uniform by the instrument that produced them.

The baseline is mandatory. No min-entropy number should be reported without running the same pipeline on /dev/urandom — the operating system's own cryptographically secure generator — and comparing the envelopes.

On one hundred 1 MB slices of /dev/urandom, the non-IID estimator produces values from 6.12 to 7.49, with a typical around 7.10. That 1.37-bit spread belongs to the estimator, not to the source. The IID estimator is much narrower — typical 7.88, spread 0.03 — but its ceiling is also the estimator's, not the source's.

The discipline is to report the envelope: typical, maximum, minimum, and spread, on both tracks, alongside a matched baseline. A single number is not a measurement. The shape of the distribution is.

The toolkit

The research is implemented as a suite of command-line tools that follow the Unix convention: read from standard input, write to standard output, compose through pipes. Every tool is a standalone binary. Every tool does one thing.

Sources

s- tools

Produce data. From the kernel's entropy pool, from files, from the speedy64 scheduler-jitter generator, or from a simple infinite zero stream for testing.

Filters

f- tools

Transform data. Deterministic PRNGs (Biski64, QXO64, xoshiro, PCG), hex encoding, byte limiting, bit-width reduction, throughput monitoring.

Terminators

t- tools

Consume data. Statistical tests (NIST SP 800-22, bit-occupancy birthday tests) and the min-entropy assessment harness that wraps the NIST SP 800-90B estimators.

Utilities

Systems tools

A timer-granularity profiler, a seekable pseudorandom filesystem (randfs), and parallel output filters that exploit O_APPEND block atomicity.

Where the operating system becomes the instrument

Three systems case studies tie the toolkit to the OS primitives it exercises. Each is a boundary between a randomness-related design and the operating system's implementation of a primitive.

Timer granularity

On macOS on Apple Silicon, thread::sleep has a granularity threshold of 7.6 microseconds. Below that, the actual delay is dominated by fixed overhead and is not controllable by the caller. High fidelity — where the requested delay and the actual delay agree to within 10% — requires delays above approximately 5 milliseconds. This measurement motivates the yield-per-emit design: the timer path has a quantisation regime, and the scheduler path does not.

Seekable pseudorandom filesystems

randfs serves infinite, deterministic, seekable pseudorandom files from a directory of 32-byte seed files. Each virtual file is i64::MAX bytes long, derived from ChaCha20 keyed on the seed. Reading byte 1018 costs the same as reading byte 0. It exists because testing tools that were never designed for enormous files requires a file that is enormous, reproducible, and random-access.

Parallel output

The parallel filters trade reproducibility for throughput by having multiple threads write to stdout concurrently, each writing complete blocks via O_APPEND. The kernel guarantees that appends are atomic, so blocks are interleaved but never split. The output is not repeatable across runs — and that non-reproducibility is the point. The filters make explicit what "parallel randomness" can and cannot mean.

The shared lesson: in each case, the operating system is not a passive substrate. It has a resolution, a semantic limit, and a guarantee that is narrower than it might appear. The interesting failures live at those boundaries.

What this is — and what it is not

The research is careful about its own limits. The speedy64 generator is a statistical source, not a cryptographic one. It passes the standard statistical tests and reports high min-entropy, but its entropy comes from shared scheduler state that a co-resident adversary can observe and influence.

Do not use it for keys, tokens, nonces, or any security-relevant output. The operating system's own CSPRNG — /dev/urandom, getrandom(2) — is the correct tool for cryptographic randomness. This research is about measurement, methodology, and understanding where randomness comes from in a software system.

The toolkit includes one cryptographic source: s-entropy, which wraps the OS CSPRNG. Everything else is for simulation, testing, procedural generation, or research.
