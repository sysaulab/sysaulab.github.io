A Field Guide — 2026

A floating-point type is not a number. It is a promise about which numbers you can name.

For decades, double was the safe default and long double was the escape hatch. In 2026 the escape hatch has become a trapdoor. On an Intel Mac, long double carries a 64-bit significand. On an Apple Silicon Mac, it is just a double wearing a longer name. The same source code, compiled for both, can produce different answers — and in at least one shipping hex editor, different answers mean rows disappear. This guide explains the three widths, maps the portability trap, and makes one request: Apple, expose _Float128 in Clang.

What is a floating-point number, really?

A floating-point value is a binary fraction with a sliding window. It stores a sign, an exponent, and a significand — the digits that actually carry precision. The exponent decides where the window sits; the significand decides how finely you can cut the interval inside that window. A float spends 24 bits on the significand. A double spends 53. A long double is supposed to spend more — but the C standard never says how much more, and it never says the extra bits have to mean the same thing on every machine.

That is the whole story in one sentence: the name of a floating-point type is not a specification of its precision. It is a hint. The actual guarantee comes from the platform ABI, and the ABI is allowed to change when the CPU architecture changes.

The core tension: a floating-point type is a contract about representable values. When the contract changes underneath you — not at runtime, but at compile time, because the target architecture changed — the program still compiles, still links, and still runs. It just stops meaning the same thing.

Width One

float — binary32

One sign bit, eight exponent bits, twenty-three fraction bits. With the implicit leading one, that is a 24-bit significand and roughly seven decimal digits of precision. A float can name about 4.3 billion distinct values, which sounds like a lot until you remember that there are infinitely many real numbers between any two of them.

Floats are wonderful for graphics, sensors, and anything where approximate is fine. They are a poor choice for money, file offsets, or identifiers.

Width Two

double — binary64

One sign bit, eleven exponent bits, fifty-two fraction bits. With the implicit leading one, that is a 53-bit significand and roughly fifteen to seventeen decimal digits. A double can represent every integer exactly up to 253, which is about nine quadrillion.

This is the workhorse. When people say “floating point” in 2026, they almost always mean binary64.

Width Three

long double — the chameleon

On x86, long double is usually the 80-bit extended format: one sign bit, fifteen exponent bits, sixty-four significand bits. It is stored in 16 bytes for alignment, but only 10 of those bytes carry value.

On Apple Silicon, long double is 64-bit double. Same name, same source, same compiler flag — 53 bits of precision instead of 64.

Why It Matters

The type is the contract

A double is portable in the way that a metre is portable: the definition is stable across borders. A long double is portable in the way that a “large coffee” is portable: the word travels, the size does not.

Code that treats long double as “a double with more bits” is making an assumption the standard never promised and the ABI is free to revoke.

Three widths, three different promises

The confusion is not that people do not know what a float is. The confusion is that the same three names describe three different hardware realities, and the names have not caught up. A float is a 32-bit IEEE binary32 value almost everywhere. A double is a 64-bit IEEE binary64 value almost everywhere. A long double is where the portability story falls apart.

On Intel, long double is an 80-bit extended format. On Apple Silicon, it is a 64-bit double. On AArch64 Linux, it may be a true 128-bit quad. The C standard permits all three, and the compiler does not warn you when you cross the border.

The Intel Inheritance

80-bit extended precision

The x87 floating-point unit introduced an 80-bit format with a 64-bit significand. It was a genuine upgrade over double in 1980, and it is still what long double means on x86-64 macOS and most x86 Unix systems.

Sixty-four significand bits can represent every integer exactly up to 264. That is enough headroom for file offsets, byte counts, and many display calculations — but only just.

The Apple Silicon Reality

long double is just double

Apple's 64-bit ARM ABI defines long double as 64-bit. An Apple DTS engineer has said it plainly: “In Apple Silicon, long doubles are just doubles,” and there is “no built-in support for floating-point numbers larger than Float64.”[reference:0]

This is legal C. It is also a silent downgrade for any code that used long double to get more than 53 bits.

The Linux Alternative

Binary128 on AArch64

On AArch64 Linux, long double is often IEEE binary128: 113 significand bits, 15 exponent bits, 128 bits total. It is a true quad-precision type, usually implemented in software but exposed as a first-class C type.

The same ARM architecture, a different operating system, and a completely different definition of long double. The type name is not the contract; the ABI is.

The Missing Name

_Float128

C23 standardises _Float128 as an optional true quad-precision type. GCC supports it. Clang supports it on some targets. Apple Clang, on macOS ARM64, does not: compiling __float128 produces “not supported on this target.”

The name exists. The precision exists in software. The portable spelling is what is missing on Apple's platform.

The portability trap

A portability bug does not usually look like a crash. It looks like a slightly wrong number. And a slightly wrong number in a display calculation can be worse than a crash, because nothing tells you it happened. The program keeps running. The output looks plausible. Only a careful comparison across architectures reveals that one build is quietly dropping data.

This is the special danger of long double. It is often chosen precisely because the developer needs more range or more exact integer representation than a double can give. On Intel, the choice works. On Apple Silicon, the choice compiles without a warning and gives the developer a double. The code that depended on 64 significand bits is now running on 53, and the failure is not a build error. It is a behavior change.

The rule: if your code's correctness depends on the number of significand bits, do not spell that dependency long double. Spell it with a type whose width is fixed by the language or the library. Otherwise you have written a program that is correct on one architecture and approximate on another.

The trap has a second jaw. Even on Intel, 80-bit extended precision is not the same as IEEE binary128. It has a 64-bit significand and a 15-bit exponent, but it is not a quad type. Code that needs 113 bits of precision cannot get there by asking for long double on any Apple platform. It can only get there by asking for a type that Apple does not currently provide.

The case: HexFiend and the disappearing rows

HexFiend is a fast, clever hex editor for macOS. It does not keep entire files in memory; it works with ranges. To draw the visible portion of a large file, it computes a floating point range — a location and a length — and uses that range to decide which rows to display. The struct is called HFFPRange, and it contains two long double values.[reference:1]

The choice was deliberate. HexFiend's own documentation explains it: a double has 53 significand bits, “so we would start to have precision problems at the high end of the range we can represent.” A long double has a 64-bit mantissa on Intel, “which means that we would start to run into trouble at the very very end of our range — barely acceptable.”[reference:2]

On Intel, the display math holds together for files up to roughly 263 bytes. On Apple Silicon, the same long double is a double, and rows begin to vanish at the high end of the file. Same source. Same editor. Different machine. Different answer.

The mechanism is straightforward once you see it. A double has 52 explicit fraction bits plus an implicit leading one. At magnitudes near 263, the spacing between adjacent representable doubles is 263−52 = 211 = 2048. If a row is 16 bytes tall, a single step in the floating-point value can skip 128 rows. The editor is not “wrong” in any way a debugger would flag. It is doing exactly what the type allows. The type just allows less on ARM than it did on Intel.

The Struct

HFFPRange

Two long double fields, location and length, used for visible line ranges and other display primitives. The design assumes 64 significand bits. On Apple Silicon, it gets 53.

The Divergence

Compiles cleanly, behaves differently

There is no compiler diagnostic for “this long double is narrower than you think.” The source is identical; only the target triple differs. This is the definition of a portability bug that survives code review.

The Consequence

Rows hidden at high offsets

At multi-exabyte offsets, the floating-point step size exceeds the row height. The view can skip entire ranges of the file without ever showing a gap. The data is still there; the display primitive can no longer address it.

The Lesson

Not a HexFiend bug

HexFiend chose long double for a reason, and that reason was valid on the platform where it was written. The bug is in the type system: Apple provides no portable way to ask for more than 53 bits of significand on Apple Silicon.

The uncomfortable part: this is not a story about one hex editor. Any macOS application that used long double as a “bigger double” — for file offsets, for accumulators, for geometric calculations, for display coordinates — inherited the same silent downgrade when it was compiled for Apple Silicon. Most of those applications will never notice. The ones that deal in very large numbers will notice at the worst possible moment.

The ask: give Clang a true quad type

Apple does not need to change long double. The 64-bit ABI is already set, and changing it would break existing binaries and existing source code. What Apple can do is add a new, opt-in type: _Float128, the C23 spelling for IEEE binary128. It has a 113-bit significand, a 15-bit exponent, and roughly 34 decimal digits of precision. It is not a replacement for double. It is a way to say, explicitly, “I need more than a double can give, and I am willing to pay for it in software.”

The LLVM project already knows how to lower f128 operations on AArch64. The missing piece is the Darwin target's willingness to expose the type. Clang on Apple platforms currently rejects __float128 with “not supported on this target,” and the LLVM issue tracker has an open request for _Float128 support. [reference:3] This is a compiler policy gap, not a hardware impossibility. Soft-float routines can provide the arithmetic; compiler-rt can provide the helpers.

What It Is

IEEE 754 binary128

One sign bit, fifteen exponent bits, one hundred and twelve fraction bits. With the implicit leading one, a 113-bit significand. This is true quad precision, not “extended” precision, and not a double-double kludge.

What It Is Not

A replacement for long double

long double keeps its current meaning on every platform. Existing code keeps its current ABI. _Float128 is additive: a new type for new code, or for code that is willing to be updated to request exactly what it needs.

The Cost

Software emulation

Apple Silicon has no native 128-bit floating-point unit. Every quad operation becomes a library call. That is slower — sometimes much slower — but speed is not the only correctness criterion. For display math, accumulators, and scientific code, the right answer at the wrong speed is still the right answer.

The Precedent

Apple already ships software floating point

Compilers routinely emulate types the hardware does not implement natively. The existence of a software implementation is not a reason to withhold the type; it is the normal mechanism by which new numeric types arrive.

What Apple should do: expose _Float128 in Apple Clang on Darwin ARM64 (and, for completeness, x86_64), implemented with compiler-rt soft-float helpers. Do not change long double. Do not change the ABI. Add the type, document it, and let developers choose it explicitly.

The alternative is what exists today: developers who need more than 53 bits either ship a third-party multiprecision library, write their own double-double arithmetic, or — worse — use long double and hope the target never changes. Apple can make the correct choice the easy choice by giving the language a name for it.

Verification notes

This guide deliberately avoids predicting future Apple releases. It describes the state of the toolchain and the ABI as of 2026, and it separates documented facts from reasonable inference.

Solid

Documented facts

A float has a 24-bit significand. A double has a 53-bit significand. x86 long double is an 80-bit extended format with a 64-bit significand. Apple's ARM64 ABI defines long double as 64-bit, and Apple DTS has confirmed that Apple Silicon has no built-in type larger than Float64. HexFiend's HFFPRange contains two long double values and its documentation explicitly reasons about the 64-bit mantissa on Intel.

Solid

The compiler gap

Apple Clang rejects __float128 on macOS targets with a “not supported on this target” error. LLVM's own issue tracker records the missing _Float128 support, and GCC has added _Float128 for Darwin AArch64 in its own tree. These are toolchain facts, not projections.

Inference

The HexFiend behavior

The arithmetic consequence is straightforward: at magnitudes near 263, a 53-bit significand cannot address every row-sized interval. HexFiend's exact threshold depends on row height, file size, and the specific display calculation. The direction of the divergence — fewer distinguishable rows on Apple Silicon — follows from the ABI, not from a bug report.

The Rule

Read the ABI, not the type name

Every claim in this guide reduces to one instruction: when precision matters, verify the significand width of the type you are using on the target you are building for. The type name is documentation. The ABI is the contract.

What to watch

Does Apple expose _Float128? The compiler already has the machinery on other targets. The question is whether Darwin's target definitions will allow the type and whether compiler-rt will ship the soft-float helpers. One WWDC session or one LLVM commit would settle it.

Does any major library adopt it? If a mainstream numerical or display library starts using _Float128 for ranges and offsets, the pressure on Apple increases. If everyone quietly switches to double-double arithmetic instead, the platform has chosen a workaround over a type.

Does the long double warning arrive? A compiler warning for “this target's long double has the same precision as double” would not fix the ABI, but it would make the trap visible. Warnings are how portability bugs become code review findings.

What would make it real: a portable _Float128 in Apple Clang, implemented in software, available alongside an unchanged long double. Existing code keeps working. New code can ask for 113 bits by name. The HexFiend class of bug becomes a compile-time choice instead of a runtime surprise.

In the end, the state of floating point in 2026 is best described as precisely imprecise. The widths are documented, the hardware is capable, and the compiler knows how to emulate what the hardware lacks. What is missing is a name that travels — a type whose meaning does not change when the target triple does. Apple can provide that name without breaking a single existing binary. It should.
